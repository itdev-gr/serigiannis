# Πλήρης έλεγχος του ζωντανού site με Claude in Chrome — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Να περπατηθεί κάθε ροή του ζωντανού site — δημόσιο και admin — με πραγματικό browser, να βρεθεί ό,τι σπάει ή παραπλανά τον χρήστη, και να παραδοθεί τεκμηριωμένη λίστα ευρημάτων με αναπαραγωγή· η βάση να μείνει **ακριβώς όπως τη βρήκαμε**.

**Architecture:** Ο έλεγχος τρέχει με τα εργαλεία `mcp__claude-in-chrome__*` πάνω στο production deployment. Κάθε task είναι μια αυτοτελής ροή που τελειώνει με καταγραμμένα ευρήματα σε ένα αρχείο, ώστε ένα task που αποτυγχάνει να μη ρίχνει τα υπόλοιπα. Ό,τι γράφεται στη βάση φέρει σταθερή σήμανση «ΔΟΚΙΜΗ CLAUDE» και καταγράφεται σε ledger· το τελευταίο task το σβήνει και επαληθεύει ότι οι μετρήσεις επέστρεψαν στα baselines.

**Tech Stack:** Claude in Chrome (MCP browser automation), Supabase Management API για baselines/καθαρισμό, το ίδιο το production Next.js site.

## Global Constraints

- **Σήμανση δοκιμαστικών δεδομένων** — υποχρεωτική σε κάθε φόρμα, ακριβώς έτσι:
  - Ονοματεπώνυμο: `ΔΟΚΙΜΗ CLAUDE — ΑΓΝΟΗΣΤΕ`

- **Στοιχεία admin:** `test@test.gr` / `123456789`. Αν η σύνδεση αποτύχει, σταμάτα και ρώτα — μην προσπαθήσεις άλλους συνδυασμούς.
- **Πρόσβαση στη βάση:** τα ερωτήματα SQL τρέχουν μέσω του Supabase Management API στο project `lucwtnzdvcpcdcmfxbqp`. Το personal access token (`sbp_…`) το δίνει ο controller στον executor τη στιγμή της εκτέλεσης — **δεν γράφεται σε αρχείο και δεν μπαίνει σε commit**. Στο πλάνο εμφανίζεται ως `$SUPABASE_PAT`.

- **Μην επισκευάζεις τίποτα κατά τη διάρκεια.** Ο έλεγχος καταγράφει· οι διορθώσεις είναι ξεχωριστή δουλειά μετά την τριάρισμα.

## Αποφάσεις

1. **Έλεγχος πάνω στο production, όχι σε preview.** Το preview δείχνει στην ίδια βάση, οπότε δεν μειώνει κανέναν κίνδυνο — και το ζητούμενο είναι να επιβεβαιωθεί αυτό ακριβώς που βλέπει ο πελάτης.
2. **Ολοκληρωμένες κρατήσεις με καθαρισμό μετά** (απόφαση του πελάτη). Χωρίς αυτό μένουν αδοκίμαστα: η οριστικοποίηση, η σελίδα επιβεβαίωσης, τα emails, η έκδοση εισιτηρίων και η εμφάνιση στο admin — δηλαδή ό,τι πονάει περισσότερο όταν σπάσει.
3. **Ο καθαρισμός γίνεται με SQL μέσω του Management API, όχι από το admin UI.** Η διαγραφή από το UI αφήνει πίσω της seat claims και εισιτήρια, και δεν επαληθεύεται με μέτρηση.
4. **Το «κάθε πιθανός συνδυασμός» μεταφράζεται σε κλάσεις ισοδυναμίας.** Οι συνδυασμοί είναι άπειροι· ο έλεγχος καλύπτει κάθε *διαφορετική συμπεριφορά*: κενό/ένα/πολλά, εντός/εκτός ορίου, έγκυρο/άκυρο, πρώτη/τελευταία επιλογή, κινητό/desktop. Το πλάνο λέει ρητά πού σταματά η κάλυψη.
5. **Δεν υπόσχεται κανείς «100% σωστό».** Ένας έλεγχος βρίσκει σφάλματα, δεν αποδεικνύει την απουσία τους. Το παραδοτέο είναι: κάθε ροή περπατήθηκε, κάθε εύρημα τεκμηριωμένο, κάθε γνωστό κενό κάλυψης δηλωμένο.

## Τι δεν καλύπτει αυτό το πλάνο, και γιατί

- **Πληρωμή με κάρτα/IRIS.** Το `PAYMENT_PROVIDER` είναι `offline`. Η ροή Viva δοκιμάζεται μόνο αφού μπουν τα `VIVA_*` κλειδιά με `VIVA_DEMO=1` — ξεχωριστός γύρος, με δικό του πλάνο.
- **Παραλαβή email.** Στέλνονται πραγματικά emails, αλλά δεν έχουμε πρόσβαση στο γραμματοκιβώτιο για να επιβεβαιώσουμε περιεχόμενο και μορφοποίηση. Ο πελάτης μπορεί να τα ελέγξει και να αναφέρει.
- **Φορτίο και ταχύτητα υπό συνθήκες.** Ένας browser δεν μετράει απόδοση αξιόπιστα· αν χρειάζεται, τρέχει ξεχωριστά με Lighthouse.
- **Άλλοι browsers.** Ο έλεγχος τρέχει σε Chrome. Safari σε iPhone είναι ο δεύτερος σε σημασία για ελληνικό κοινό και δεν καλύπτεται εδώ.
- **Εξαντλητικές μεταθέσεις.** 252 εκδρομές × κατηγορίες × ημερομηνίες δεν περπατιούνται μία-μία. Ο έλεγχος καλύπτει κλάσεις ισοδυναμίας και τα άκρα τους, όπως λέει η Απόφαση 4.
